# zUI — TOOLCHAIN GUIDE

zUI is a themeable UI subsystem that sits on top of a host application (a music
app, a game engine, a project-management app, …) so every one of them presents
the same UI. This file tells an agent working in one of those projects how to
pull zUI in and use it. The visual rules are in Part 2.

Repo: https://github.com/CoolBeanGames/zUI
Reference docs (read these before extending anything):
  README.md                     overview + architecture
  core/PROTOCOL.md              host <-> UI message + component-IO contract
  core/css/THEMES.md            theme catalogue + how to add one
  core/css/TYPOGRAPHY.md        the type token system
  compiler/GRAMMAR.md           the ZSL / ZML UI language
  core/icons/README.md          the icon set

# PART 1 — USING zUI

## 1. Get it

Vendor it as a git submodule (preferred) or a plain clone:

    git submodule add https://github.com/CoolBeanGames/zUI.git third_party/zui
    git -C third_party/zui checkout main

Everything the host needs is under `core/` (CSS + one JS file) plus one binding:

    core/css/zui.css              single stylesheet entry point
    core/css/themes/holo.css      default theme (dark Android-Holo look)
    core/css/themes/clean.css     light alternative
    core/js/zui.js                runtime
    core/icons/                   icon sprite (+ sprite.js loader)
    bindings/csharp/ZUI.csproj    .NET host binding (WebView2)
    bindings/cpp/                 C++ host binding (WebView2 backend included)

## 2. Embed it

zUI renders inside a web view the host owns. Pick the binding for your language;
both embed the identical `core/` assets, so the result is pixel-identical.

C# (WinForms/WPF + WebView2):

    var ui = new ZUI.ZuiHost(webView2Control);
    await ui.InitializeAsync();
    await ui.LoadAsync("ui/main.html");        // your zUI document
    ui.On("save", json => Save(json));
    ui.Send("theme", "holo");

C++ (Win32 + WebView2):

    zui::Host ui(hwnd);
    ui.set_core_root("zui");
    ui.load("ui/main.html");
    ui.on("save", [](const std::string& j){ save(j); });
    ui.send("theme", "\"holo\"");

Runnable end-to-end examples: `samples/csharp/`, `samples/cpp/`. The C# sample
builds with `build.ps1`.

A zUI document is a normal HTML file that links the core:

    <html data-zui-theme="holo">
    <link rel="stylesheet" href="zui/css/zui.css">
    <link rel="stylesheet" href="zui/css/themes/holo.css">
    <script src="zui/icons/sprite.js"></script>
    <script src="zui/js/zui.js"></script>

## 3. Author the UI

Write screens in **ZSL** (brace) or **ZML** (angle-bracket) — same tree, same
output, auto-detected — and compile ahead of time (never interpreted at runtime):

    py third_party/zui/compiler/zslc.py ui/main.zml --backend html   -o ui/main.html
    py third_party/zui/compiler/zslc.py ui/main.zml --backend csharp -o Ui.g.cs
    py third_party/zui/compiler/zslc.py ui/main.zml --backend cpp    -o ui.g.cpp

Layout is flow/flex (no x/y): nest `row` / `col`, mark the stretchy one `fill`,
use `sidebar` / `splitter` / `grid`, the `gap-*` / `pad-*` scale, and
`panel` for bordered regions. See `compiler/GRAMMAR.md` for every node.

## 4. Talk to it

One JSON channel: `zui.send(channel, payload)` / `zui.receive(channel, fn)` in
the page; `host.Send` / `host.On` (C#) or `ui.send` / `ui.on` (C++) on the host.

Read or write ANY component tagged `data-zui-id` (ZSL/ZML `export="name"`):

    zui.values() / zui.field(id) / zui.set(id, value)     // in the page
    channels: value, set, set-many, query, submit          // over the bus

Covers text, checkbox, radio, select, progress, button clicks/state, sliders and
scroll positions, both directions. Full table in `core/PROTOCOL.md`.

## 5. Keep it consistent

- `build.ps1 -Config test` runs the compiler tests, the runtime IO self-test and
  `tests/check-tokens.py` (which fails if any component CSS hard-codes a colour).
- When you add a reusable widget: give it an IO adapter in `core/js/zui.js`, a
  row in `core/PROTOCOL.md`, and a token-only stylesheet (no literal colours).
- A new theme is ONE file re-declaring the tokens — never touch component CSS.

# PART 2 — VISUAL DESIGN STANDARD

Treat these as requirements whenever creating or modifying UI. New UI must look
like it was there from the start. Do NOT redesign the visual identity unless
explicitly told to.

The structure, spacing, typography, density and interaction rules apply to every
theme; only the palette changes between them.

## Identity

Default theme **holo** — Google's Android Holo: dark chrome (`#0c0c0c` app,
`#1b1b1b` surfaces), Holo-blue `#33b5e5` accent, thin `#2c2c2c` dividers,
uppercase accent-coloured section headers with an underline rule, blue-tinted
selection with a left accent bar, light text.

Alternative theme **clean** — a light, neutral "native Windows utility" palette
(off-white app, white surfaces, muted desaturated-blue accent).

Both should feel: CLEAN · QUIET · FAST · NATIVE · COMPACT · ORGANIZED ·
FUNCTIONAL. Not: FLASHY · WEB-LIKE · MOBILE-FIRST · CARD-HEAVY · OVERSIZED ·
DECORATIVE.

Avoid: gradients (except the very subtle ones already in tokens), glassmorphism,
large rounded cards, oversized controls, giant headings, excessive whitespace,
floating elements, decorative shadows, pill controls without a functional reason.

## Structure

Strong horizontal hierarchy, separated by thin borders not big containers:
  native title bar → application menu → primary nav strip → workspace →
  status/device bar → contextual/playback bar.

Sidebars are narrow and functional (the `tree` component); square selection,
pale-accent highlight, small secondary section headings.

Main content is panels / columns / lists / grids / tables that share one
background and are divided by 1px borders — never independent floating cards.

## Type

Platform-native UI font (Segoe UI first), no web fonts. Compact scale
(11 / 13 / 14 / 20px). Hierarchy from **weight**, not dramatic size jumps.
Never hard-code font metrics — use the `--zui-fs-*` tokens.

## Controls

Buttons: compact, rectangular, thin border, very light fill, minimal radius —
not web CTAs. Inputs: white/light fill, thin border, small radius, compact
height — not giant/mobile. Tables: compact rows, subtle separators, clear
headings, left-aligned; highlight rows only for a functional reason (selection,
missing metadata, error). No decorative zebra striping.

## Spacing & borders

Spacing scale: 4 / 8 / 12 / 16 / 24 px (`--zui-space-*`). Use borders heavily
but subtly (1px, low-contrast, `--zui-border`). Information density like a
desktop productivity app, not a touch UI.

## Iconography

Small, monochrome, line-based, consistent weight, from `core/icons/` — never
emoji as UI icons, never mixed icon styles.

## Interaction

Behave like a desktop app: right-click context menus, double-click actions, drag
and drop, keyboard shortcuts incl. Ctrl+Z / Ctrl+Y, Tab order, multi / shift /
ctrl selection, rename-in-place, tooltips, standard Windows key behaviour. All of
this is centralised in `core/js/zui.js` — reuse it, don't reimplement.

## Consistency rule

Before building any new UI: inspect existing components, reuse existing
styles/patterns, match existing spacing/sizing/typography/borders/behaviour. If
a feature needs a new reusable pattern, add it as a shared component + token-only
stylesheet so later work reuses it. A user must not be able to tell which screens
were built at different times or by different agents.
