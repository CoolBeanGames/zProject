read through tasks.xml and complete tasks in the order they are presented. work through the list until reaching the end or you run out of usage. as you finish a task update the xml to mark it as done, as you begin mark it as in-progress. save the xml every time you make a change.

when finishing a task, set its dateFinished field to the current local date and time before setting done=true. work completed today is kept in finished_today.xml and shown in Finished Today; older completed work rolls into archive.xml on reload. use `operator get_finished_today <project>` to read today's completed work, but never process it as active work.

when starting any task, create subtasks breaking down the work using `operator new_subtask <id> <text>`. as each subtask is completed, check it off immediately using `operator subtask_done <id> <index> true`. a task is NOT complete until all subtasks are finished and checked off.

if a task has a branch specified, agents must be branch-aware and complete tasks on that branch. if <merge> is true, merge the branch into main upon completion.

if a task has the tag commit set to true then commit the project and push to github with a meaningful message of all the changes made. Add notes about the changes you made, log all files, and move on to the next task.

the task is NOT complete unless the requirements have been met, if a task is impossible to complete add an "error" flag, set it to true, and add error message text in before saving XML and end execution of tasks there, notifiying your chat of the error and the taskID. 

if the task has a build tag set to true, the project should be built to project_root/builds/debug, if you need to test build to project_root/builds/test, if it has a release tag set use project_root/builds/release

if a task has <priority>true</priority>, process it before EVERY non-priority task, including in-progress tasks and bugs. if multiple tasks have priority set, process them in their existing listing order.

if a task is a bug, it takes priority over ordinary tasks.

if a task is blocked by another task, finish the task that is blocking it first, then return to the first task.

if a non-priority task is in-progress it takes priority over bugs and other ordinary tasks.

COMPLETELY ignore the acrhive tags contents, dont even proccess it once you see it.

If a project is a release build, then also release a github release with full patch notes since the last release, tag it as project_name_build# build# is the most recent build# +1 use the gh cli to do this.

NOTES are informational queue items whose XML contains a <note> element instead of a <prompt>. Read each note when you reach it; do not take an agent lock, set in-progress, create subtasks, add agent notes/files-changed metadata, build, commit, release, or otherwise process it as a task. Keep its name and branch unchanged. If <clearAfterReading>true</clearAfterReading>, archive it immediately after reading with `operator archive <note_id>`; if false, leave it unchanged and continue to the next queue item. A user may mark a note done manually.

STOP EXECUTION markers are queue items whose XML contains <stopExecution>true</stopExecution>. When one is reached in queue order, do not lock, modify, archive, delete, or otherwise process the marker, and do not process any item after it. Stop immediately, report the marker ID to the user, and await further instructions. Resume beyond the marker only after the user explicitly directs you to proceed or the marker has been removed or moved. Stop markers are not tasks: never add subtasks or task metadata to them, and never include them in CSV task exports.
